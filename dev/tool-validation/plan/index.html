Tool validation plan¶

How the static-analysis toolchain behind the MISRA C++:2023 compliance matrix is validated for use under the quality management system of an IEC 62304 Class C product, and how the evidence stays current.

Purpose and scope¶

The compliance matrix says, guideline by guideline, which tool decides it. A tool that decides a guideline replaces a reviewer for that guideline. If the tool misses a violation, nobody else is looking. Every such claim therefore needs evidence that the tool, in our configuration, does what the matrix says. This plan defines that evidence: its requirements, test cases, acceptance criteria, records and re-validation.

In scope are the tools whose output is verification evidence for C++ code in drivers, libraries, HALs and firmware:

  • compiler warnings
  • clang-tidy
  • cppcheck
  • the CodeQL MISRA C++:2023 pack and our own C++20 profile pack
  • the handbook checks
  • the scripts of ru-misra that run them

Compilers as code generators, debuggers and the documentation tools are out of scope.

Intended use and confidence classification¶

Tool impact is TI2 for every tool here: each can fail to report a violation it is relied on to find. The tool error detection (TD) column says how likely a tool error is to be caught later in our process. The method is ISO 26262-8 Table 3: TI2 with TD1 gives TCL1, with TD2 gives TCL2, with TD3 gives TCL3.

Tool Intended use TD and reasoning TCL Confidence from

TD2: the warnings are front-end checks on syntax, and the CodeQL queries cover most of the same guidelines independently. TCL2 Validation of the tool (suite, every claim, GCC 14, Clang 18, Arm GNU 14.3); confidence from use
clang-tidy 20.1.0 Decide the guidelines the matrix assigns to a check, with the CheckOptions the suite records. TD2: most of these guidelines also have a CodeQL query. TCL2 Validation of the tool (suite); confidence from use
CodeQL 2.21.4 with codeql/misra-cpp-coding-standards 2.62.0 Report violations of 175 guidelines. The pack's own validation covers C++14/17 with gcc 8.4, clang 10 and qcc 8.3 only, not our C++20 and compilers. A TCL2 or TCL3 tool decides a guideline only for the requirements that pass. A requirement recorded as an anomaly does not decide anything. That aspect of the guideline keeps review, or the tool named in the anomaly's disposition.

Analysing compiled code¶

CodeQL's C/C++ extractor builds its database from the compiler invocations it traces. build-mode: none exists for C/C++, as a preview from June 2025 and generally available since October 2025 in CLI 2.23.3. It infers the translation units and flags from the files instead. GitHub's documentation says this may give less accurate results, especially with macros or defines that are not in headers. The pack's user manual requires a clean, full build of the code. Both sources: build options for compiled languages and the pack's user manual.

Decision.

  • Only traced builds. ru-misra and the suite analyse traced builds only, from a fresh build directory, with the real compiler command lines CMake writes to compile_commands.json. Build-mode none is not used.
  • Two configurations. The preprocessor takes different paths per target, so every configuration the drivers ship is a separate database:
  • host (g++);
  • cortex-m: the Arm GNU toolchain with the cortex-m4f flags of ru-cross-build.
  • ESP-IDF not yet. An ESP-IDF (Xtensa) configuration is not analysed yet; see the limitations.
  • Same compile databases for the other tools. clang-tidy and cppcheck run on the same compile databases as the CodeQL scan.
  • Run-time checks. The extraction checks prove at every run that each translation unit of the build, and each source file under the analysed paths, is in the database.

Requirements¶

Each claim "tool T decides guideline G with rule id R" is a requirement with a stable id TV-<TOOL>-<GUIDELINE>-<NN>, for example TV-CQL-RULE-8-2-5-01:

Source of the claim Requirements
The matrix's non-partial compiler entries One per compiler (GCC, CLANG) and diagnostic; the GCC claim also for the cross GCC (GCCARM)
The matrix's non-partial clang-tidy entries One per check (TIDY)
The pack's default suite One per query of each applicable guideline (CQL), 221 queries for 175 guidelines, minus the not-applicable guidelines
The own profile pack One per query (CQL, guideline KB-CPP-NNN)

validate.py record derives the requirements from the matrix at the pinned handbook commit, from the pack's supported list (tests/misra-validation/codeql-supported.json, read from the pinned pack's query metadata) and from the profile pack. A new matrix claim is a new requirement, and it fails until a test proves it.

Test cases¶

A test case is a directory under tests/misra-validation/cases/ (or codeql/<pack>/validation/) with:

  • Seeded violations (bad*): true positives, including the edge cases the guideline targets. Each seeded violation ends its line with // seeded, and every claimed tool must report on that line: a file that seeds three forms proves three detections, not one. // seeded: codeql (or another list of tools) limits a marker to the tools that report the form on that line. A bad file without a marker is a malformed case.
  • Compliant code (ok*): true negatives, including near misses that must not be flagged. Every compliant file must build without a warning with the org flags on GCC and Clang. For the Cortex-M target it must also build with the cross GCC.
  • The exact rule id in case.yml. That is the warning option, or the clang-tidy check name, or the CodeQL query id. A query's result must also carry the guideline's tag (external/misra/id/rule-x-y-z).

The snippets are our own. None is copied from the MISRA documents, whose text and examples are licensed. Each case was reviewed against the guideline by a reviewer who did not write it (bad files violate in every seeded form, ok files comply, near misses sit at the boundary); the review findings were fixed before the suite's first release. A CodeQL query is shown on two databases per target, one of all seeded violations and one of all compliant files. Each is built by a traced compile of each file. Both are analysed with the full default suites, so every result of every query on compliant code is seen. A result of another query on a compliant file must be listed in the case's other_findings with a reason. A false positive of the pack is recorded there as misfire: ... and in the anomaly log. The suite runs on every pull request and every push to main (the self-CI, ci-misra.yml). It runs locally with tests/misra-validation/validate.py local.

Acceptance criteria¶

Status Meaning Accepted when
pass On every target of every case of the requirement, the tool reports the rule id on every marked line of every seeded file and nothing on every compliant file, except recorded false positives (listed with the requirement) Always
anomaly A recorded false negative of the rule id in any case (or only recorded anomalies), with a log entry and a disposition. The rule id is then partial for the guideline Only for pack and profile queries; the guideline keeps the mitigation the disposition names
fail A test does not hold, or did not run on a target Never
no test No case for the requirement Never

The self-CI fails (record --check) when any of these holds:

  • a matrix claim (compiler, clang-tidy) is not pass;
  • a pack or profile query is fail or no test;
  • a compliant file draws an unreviewed result;
  • the anomaly log and the cases disagree;
  • the committed record does not match the run.

Records¶

Record Where Content
Validation record tests/misra-validation/validation-record.json, committed Hashes of the toolchain, suite and matrix; exact tool versions; every requirement with its tests, runs and status
Traceability traceability.md, committed Requirement → tests → result; guideline → tools of the matrix, with what is validated
Validation report validation-report.md, artifact tool-validation of every self-CI run, attached to each ci-tools release Tool versions and hashes, results by tool, open problems, anomalies with dispositions, limitations, every test result
Anomaly log tests/misra-validation/anomalies.yml Every known false negative and false positive, how it was found, its disposition

The report is the record an auditor reads. The release attaches the report of the self-CI run that released it.

Re-validation¶

A change to any of these changes a validated tool or its configuration:

  • toolchain.json
  • the runner's compiler versions
  • the compile flags
  • a clang-tidy option
  • a case
  • a profile query
  • validate.py
  • the pinned handbook commit (the matrix)

Each of these changes the record: its hashes, its versions or its results. The record check then fails the self-CI until the validation has run again and the regenerated record and traceability are committed from that run's tool-validation artifact. A version bump therefore cannot merge without its validation evidence. An update of the runner image that changes a compiler fails the self-CI the same way.

Run-time assurance¶

Validation shows the tools work. Run-time assurance shows they worked on this scan:

  • Canary. A file with known violations (tools/misra/canary/ru_misra_canary.cpp) is compiled into every database. If any of its expected query results is missing, the scan fails.
  • Extraction coverage. Every translation unit of compile_commands.json must be in the database. So must every source file under the analysed paths, through some translation unit. An extractor error (severity 4 or 5) fails the scan.
  • Flags. Each translation unit is checked for the org flags. At the safety level, a missing flag fails, because the compiler-decided guidelines would not be enforced.
  • Suppressions. Every marker must cite a record and deviate a finding of that record's guideline.

What the tests cannot prove¶

The review checklist covers what remains:

  • Absence of violations of an undecidable guideline. Passing tests show detection of the seeded forms, not completeness.
  • System-scope guidelines across a whole program, beyond the translation units of the analysed build.
  • Code paths no analysed configuration compiles, today ESP-IDF (Xtensa).
  • The guidelines no tool covers (Dir 0.3.2, and the review-only parts of others).

Licence of CodeQL¶

The CodeQL CLI is licensed per user, and only for these purposes:

  • academic research;
  • demonstrating the software;
  • testing OSI-licensed queries;
  • analysis of an Open Source Codebase: a codebase released under an OSI-approved licence;
  • for an Open Source Codebase hosted on GitHub.com, creating databases in automated analysis, CI or CD.

The License Restrictions exclude "any codebase that is not an Open Source Codebase". Their own example of such a codebase is a private repository. Those restrictions do not apply under a paid GitHub Advanced Security licence (terms). This repository is public and MIT, so the suite runs here and locally. A private driver may not be analysed, in CI or locally, until it is public under its OSI licence, or the organisation buys the licence. ru-misra enforces this before it downloads anything.
